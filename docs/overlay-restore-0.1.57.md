# Overlay restore animation - 0.1.57

Opening a session by double-click or Copilot shortcut now grows and fades the selected overlay over 260 ms while the editor restores/maximizes and opens the chat. It starts from the current visible tab or panel bounds and stays inside the chat's display lane. An already expanded panel gets a small zoom instead of jumping back to a tab. Cached message painting and the existing high-resolution frame timer supply the animation.

Editor activation runs on a worker with an explicitly created Windows message queue, which is needed for input-thread attachment. The activation and the animation begin from the same open request. The overlay retains its own frame/input loop while activation runs. The decorative overlay is click-through immediately, and its mouse actions and shortcut binding are suspended to prevent duplicate opens. Other tabs keep their state.

Success hides the overlay after the fade and preserves the existing protection against stale frames redisplaying the opened chat. A failure restores the panel and its controls without acknowledging the chat. Disconnected requests fail closed, and a pending request releases the visual state after a bounded three-second wait. Windows client-area and minimize/maximize animation preferences skip the decorative transition when animations are disabled. Minimizing the same editor during the opening transition ends that decorative expansion so the existing minimize path can take over.

This is an accompanying overlay animation; Windows still renders the actual editor-window animation. It does not replace DWM or claim identical per-frame easing. Click-through uses the behavior documented for transparent layered windows in Microsoft's [Window Features](https://learn.microsoft.com/en-us/windows/win32/winmsg/window-features#layered-windows).

All 127 native checks passed in the full run, including the explicit desktop overlay tests and all 50 isolated extension/native pipe exchanges. Clippy passed for all targets with warnings denied. The new native test kept activation pending for 150 ms and observed 10 distinct widths and 9 opacity values during that interval, demonstrating that restoration does not block painting. The complete transition hid at 273.3 ms (275.3 ms in the first targeted run), including frame scheduling and observation overhead.

Coverage includes successful and failed async opens, invalid/closed target rejection, disconnected requests, duplicate input suppression, click-through style, geometry at several display scales, reduced motion, stale cached frames, return-on-focus-loss, and the existing mouse, keyboard, minimize, hover, and completion behavior. Tests use owned overlays and simulated activation results; no real editor window was opened or activated by these tests. Measurements describe native geometry and opacity delivery, not physical display presentation.
