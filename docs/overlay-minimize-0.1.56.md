# Overlay minimize timing - 0.1.56

Minimizing VS Code previously waited for a 250 ms reader poll and then another independent 250 ms native-window poll before beginning a fresh 260 ms shrink. The overlay could therefore start after the editor had already minimized.

The native overlays now subscribe to Windows foreground and minimize/restore events. The focused chat remains in the bounded three-chat cache, hidden while it is viewed. A minimize event reveals its cached frame immediately, without reading transcripts or waiting for the reader. Fresh frames also notify the native windows directly; the UI polling timer is only a one-second fallback. Message reads remain on the existing background worker.

The shrink uses the Windows event timestamp, accounting for delayed delivery and 32-bit tick wrap. A late event joins the transition already in progress or shows the finished tab. Minimize and foreground-loss notifications share one start. A later reader epoch acknowledges that transition instead of minimizing a panel that was just reopened. Restoration resets the event, and switching chats within one focused editor still returns the previous chat as a minimized tab.

The callbacks only post messages to owned overlay windows. Subscriptions and publication destinations are removed on shutdown. Windows client-area and minimize-animation preferences are both respected. Existing cached bitmap rendering, 60 Hz frame deadlines, no-focus-stealing behavior, hover controls, completion indicators, and Copilot shortcuts are preserved.

Windows supplies a minimize event and timestamp, not a supported shared progress value for another window's DWM animation. The overlay therefore aligns its existing 260 ms easing to the event; this is not a claim of identical compositor frames, easing, or completion time for every Windows theme or animation customization. `EVENT_SYSTEM_MINIMIZEEND` denotes restoration, not the final frame of minimizing. See Microsoft's [event definitions](https://learn.microsoft.com/en-us/windows/win32/winauto/event-constants), [SetWinEventHook](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwineventhook), and [WinEvent callback timestamp](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nc-winuser-wineventproc).

Validation covered 122 unique native checks across the full run and a targeted pipe rerun. The final 55 overlay checks passed after the chat-switch refinement; Clippy passed with warnings denied. The native cached-minimize test measured 4.50 ms to the first visible window and 15 geometry changes during the shrink. Earlier runs measured 4.74 and 13.39 ms. These measure native window geometry and visibility, not physical display presentation. Tests cover delayed delivery, restored/hidden cached chats, reopening before the reader catches up, chat switching without a foreground event, hook delivery and cleanup, and the existing overlay controls. No real editor window was minimized or activated by the tests.

The full run encountered an intermittent `ENOENT` in the pre-existing isolated pipe integration test. Its targeted rerun completed all 50 requests with no failures (0.224 ms median, 3.947 ms maximum). No pipe implementation was changed for this update.
