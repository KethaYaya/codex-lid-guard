# Overlay restore continuity - 0.1.58

Version 0.1.57 replaced a collapsed tab with a full message bitmap on the first frame and independently stretched it toward a larger card. Its 260 ms animation also started before the activation worker reached the editor restore call. Those changes could show a content jump followed by an unrelated zoom alongside Windows' restore animation.

The new transition captures only the overlay's existing painted pixels and actual rounded window region. The first composited frame is identical to that source, including a tab and panel partway through hover expansion. It grows proportionally while fading over 180 ms. Right-side panels, tab expansion, and restore motion stay attached to the display edge; the previous 20-DIP horizontal gap is removed. Width and height are interpolated independently of position to prevent one-pixel size reversals from rounding moving edges separately.

The worker signals immediately before calling ShowWindow, after its startup, HWND/process validation, and foreground input attachment. The overlay holds its original appearance without an animation timer until that signal. Delayed delivery joins the event's timestamp; duplicate notifications cannot restart the animation. Successful completion provides a fallback if a notification is missing. Windows still draws the editor itself, so this synchronizes the start of the accompanying transition rather than controlling DWM's per-frame easing.

Each animated frame uses one UpdateLayeredWindow call for position, size, shape, content, and opacity. The source and output images are allocated once, and frames perform no message layout or bitmap allocation. Returning to normal painting resets the layered presentation mode and restores the rounded region, including after an unsuccessful open. Painting and activity timers cannot overwrite the frozen transition. Mouse input passes through while opening, and shortcut routing, independent tabs, completion acknowledgement, stale-frame suppression, reduced motion, and failure recovery retain their previous behavior.

The implementation follows Microsoft's [UpdateLayeredWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-updatelayeredwindow), [SetLayeredWindowAttributes](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setlayeredwindowattributes), and [CreateDIBSection](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/nf-wingdi-createdibsection) requirements, including the presentation-mode reset and flushing GDI before accessing image memory.

Validation covers exact first-frame pixels and transparent regions for collapsed, partially expanded, and fully expanded overlays at 100% and 200% scaling; stable bitmap handles across 72 frames; delayed activation; monotonic geometry; duplicate notifications; success/failure; and the existing mouse, keyboard, hover, minimize, and completion behavior. The owned overlay integration test holds activation for 100 ms and verifies that the tab remains unchanged, then signals restoration and checks motion, click-through, cleanup, stale-frame suppression, and control recovery.

The full suite run passed 128 of 129 native checks; the existing isolated pipe test hit its intermittent ENOENT connection race. A targeted rerun also hit the race, then the next targeted run completed all 50 exchanges successfully. All overlay checks passed, and Clippy passed with warnings denied. No pipe implementation or test code was changed for this animation fix. After the final edge-alignment adjustment, all 62 overlay checks passed, including targeted reruns of two desktop checks affected by concurrent user input. The synthetic three-panel test now lets the real pointer pass through its owned windows so real mouse movement cannot compete with injected hover events. Restore presentation measured 1.814 ms median, 5.162 ms p95, and 6.710 ms maximum over 72 frames, including 200% scaling. The owned overlay hid 185.8955 ms after the restore signal. These are native rendering and geometry measurements on test-owned windows; they do not measure physical display presentation or prove frame-for-frame alignment with a real VS Code restore.
